# Worktree Delivery Governance

## Product boundary

Worktree Delivery is a stack-independent capability in the
`@realpkuasule/harness-automation` package. It reuses the v2 policy compiler,
canonical SHA-256 plans, argv execution, atomic writes, drift checks, rollback,
and receipts.

It is exposed through two Skill entry points:

- `harness-automation` initializes repository policy;
- `manage-worktree-delivery` operates worktree lifecycle through the shared CLI.

The default is audit-only. Installing or upgrading the package creates no
worktrees and deletes no state. Persistent operations require dry-run planning.
Manual mode uses exact-hash apply; an optional host-local `delegated-ai` policy
may authorize explicitly allowlisted lifecycle plans through an independent,
no-tools reviewer decision bound to the same plan hash.

## Layers

### Policy plane

`.harness/worktree-delivery.json` is generated by an approved configuration
plan. It records only portable mode, the management branch selector, capacity,
lease/review/remote retention, remote deletion policy, and Provider mapping.
Host-specific allowed and protected roots live in
`<git-common-dir>/harness/worktree-delivery/host-binding.json`. One configure
plan hashes and applies both files.

New host bindings may additionally select `container-v1`: a non-Git workspace
container contains exactly `main/` for the protected management checkout and
`worktrees/` for direct-child persistent Issue checkouts. The binding stores
canonical absolute container/main/worktrees paths; portable repository policy
stores none of them. Configure planning is zero-lifecycle-side-effect, while an
approved configure apply may create only an absent, exact, empty `worktrees/`
root and records that creation in its receipt. Existing bindings with no
topology remain `legacy-flat` and are never inferred, moved, or rewritten.

Policy v2 also supports optional orthogonal arrays:

```json
{
  "deliveryProfiles": ["worktree-delivery"],
  "domainProfiles": ["game-development"]
}
```

Neither array changes `StackProfile` or inferred stacks. Domain profiles only
append constraints.

### Observation plane

The service obtains machine-readable Git state with argv calls:

- `git rev-parse --show-toplevel`;
- `git rev-parse --path-format=absolute --git-common-dir`;
- `git worktree list --porcelain -z`;
- `git status --porcelain=v1 -z`;
- `git for-each-ref` and `git rev-list`.

Paths are canonicalized before comparison. Read-only status and audit do not
create `.harness`, common-dir state, worktrees, branches, or locks.

Observed state separates:

- `configured`: an approved worktree config exists;
- `loaded`: Git state and configuration were parsed;
- `enforced`: a deterministic checker is available;
- `passing`: the current observation satisfies the checker.

The canonical observation hash includes repository config and host-binding
hashes, refs, worktree state, leases, Provider observation, and parse errors.
Main-checkout dirty state is excluded because writing the immutable plan itself
would otherwise invalidate that plan; managed worktree dirty state remains
included.

Audit resolves exactly one management checkout from `managementBranch`, exempts
the current checkout only when it is detached, and rejects every other
secondary worktree without a lease. It also rejects missing or ambiguous
management checkouts, leases without matching worktrees, Project-backed Issues
missing from the configured Project, and leases whose heartbeat exceeds
`leaseTtlHours`.

### Runtime plane

Repository-scoped runtime state lives under the resolved Git common dir:

```text
<git-common-dir>/harness/worktree-delivery/
  apply.lock
  review.lock
  host-binding.json
  ai-decisions/<decision-id>.json
  leases/<sha256(work-item)>.json
  receipts/<change-id>.json
```

Temporary Review recovery receipts live in the host OS state directory.
Credentials are never stored.

## Lifecycle transactions

### Configure

`worktree configure` writes a plan containing the current hashes and complete
replacement content for both the portable repository policy and host-local
binding. Apply rechecks the observation and both file hashes before atomic
writes. Failure compensation and rollback restore both previous contents.
For `container-v1`, they also remove only the directory created by that receipt,
and only while it is still empty; otherwise rollback fails closed.

### Legacy migration

`worktree migrate` is intentionally plan-only. It captures all lease, binding,
management-checkout, ref, worktree, dirty, unique/unpushed, and path evidence
for a requested container target, but it cannot be applied. Relocating an
existing Git checkout and re-registering worktrees needs a separately designed
transaction and exact-hash approval; configure must never masquerade as that
migration.

### Delegated AI authorization

The host binding may name one Claude Code model and an operation allowlist.
`worktree apply-ai` runs that reviewer in a fresh no-tools, no-persistence
process and records `approve`, `deny`, or `abstain` as a canonical decision.
An approval binds the plan, plain-language intent, host policy, observation,
model, and TTL. It does not replace deterministic validation: apply rechecks
the plan under the repository lock and records the decision and policy hashes
in its receipt. Reviewer failure or uncertainty creates no lifecycle mutation.
Close and recover also require zero ignored, unique, and unpushed evidence.
Configure and rollback are never AI-delegated.

### Allocate

`worktree allocate` requires a work item, branch, absolute path, owner, and
start point. Planning rejects duplicate work-item leases, duplicate paths,
checked-out branches, protected roots, paths outside allowed roots, Provider
failure, and capacity overflow.

Apply acquires the repository lock, rechecks the complete observation hash,
creates or checks out the branch through `git worktree add`, verifies HEAD, and
then writes the lease. Failure compensates only the clean worktree/branch
created by that same approved transaction.

An applied allocation cannot be deleted with `rollback`; it must pass a new
exact-hash close plan because it may now contain valuable work.

### Adopt

`worktree adopt --manifest <json>` migrates one or more already registered
persistent worktrees into lease governance. The manifest supplies only the
intended work item, owner/thread, absolute path, and current branch. Planning
observes and hash-binds current HEAD/branch ref, Git index, dirty files and
binary patch, lease absence, host binding, capacity, and configured Provider
Issue/Project state.

Apply acquires the existing repository transaction lock and repeats the full
batch observation before writing a receipt or lease. It writes leases only
after every item passes. A handled mid-write failure removes only unchanged
leases created by that transaction; no adopt path invokes worktree, checkout,
branch, ref, index, or working-tree mutation commands.

Adopt rollback is metadata-only. It removes the complete batch of unchanged
leases only while no later lifecycle receipt has consumed one of their hashes.
It never removes or recreates an adopted worktree.

### Close

Close planning requires:

- exactly one lease for the work item;
- a matching path and branch;
- a clean worktree;
- an Accepted Commit equal to current HEAD;
- at least one remote ref containing that commit.

Apply rechecks every precondition, removes the exact worktree without force,
and removes its lease. Local and remote branches remain. Rollback can recreate
the worktree only while its branch still points to the recorded commit.

### Review

Review is explicitly temporary rather than persistent:

1. acquire the one-review repository lock;
2. create an OS temporary directory;
3. add a detached worktree for the exact commit;
4. run one argv command;
5. remove the worktree immediately if clean;
6. preserve it with a durable receipt if dirty or cleanup is unsafe.

A process killed before cleanup leaves an active receipt. `retention-audit`
reports receipts and lease heartbeats older than their configured TTL. It never
force-cleans them.

## Dirty-content evidence

Dirty worktrees block close and automatic cleanup. Read-only observation
records:

- repository-relative path and Git status;
- byte size;
- SHA-256 of file or symlink content;
- size and SHA-256 of the tracked binary patch.

Creating a patch file, tar archive, quarantine copy, or disposition plan is a
separate owner-approved action. Business value, asset rights, legal status,
and long-running debugging value are guidance, not deterministic policy.

## Provider and Agent adapters

The portable baseline has no Provider dependency.

The GitHub adapter uses `gh` with argv and configuration-provided repository,
Project owner/number, status field, and Done values. Issue state comes from the
REST API. When Project mapping is configured, one batched GraphQL request reads
only the relevant Issues' ProjectV2 items; the same observation is reused
through planning and drift checks instead of listing the whole Project or
querying it once per lease. Project fields are not hard-coded. A GraphQL quota
failure reports `GITHUB_GRAPHQL_RATE_LIMITED` with the REST rate-limit reset
time when available. Local policies remain observable, but lifecycle mutations
still fail closed while required Project state is unavailable. GitLab and Jira
configuration is accepted but reports `blocked` until a real adapter is
installed.

Agent behavior is CLI-first. Claude Code, Codex, DeepSeek/GLM, and unknown
agents use the same command contract. An optional Codex Thread adapter may add
thread-state evidence later; it cannot weaken the portable lease rules.

## CI boundary

CI normally cannot see development-machine worktrees or common-dir leases.
`check --mode ci` therefore reports host-local workspace enforcement as
`blocked` while continuing repository-visible gates. Session checks run the
real local audit and fail when it does not pass.

## Safety invariants

- one work item has at most one persistent lease;
- management, status, audit, retention audit, and planning create zero
  worktrees;
- Review is detached, temporary, branchless, and serialized;
- all mutation targets are canonical absolute paths;
- remote branch deletion is always disabled;
- no operation uses `rm -rf`, `reset --hard`, worktree force removal,
  `branch -D`, or `git clean -f/-x`;
- apply is locked, drift-checked, and idempotent;
- every lifecycle attempt that begins mutation leaves a durable receipt; preflight drift writes none.

## Compatibility and migration

All Policy v2 profile fields are optional in the JSON Schema, so existing
policies remain valid. Existing stack profiles, custom stacks, CLI commands,
and legacy task-board compatibility remain unchanged.

Existing worktrees are not automatically adopted or cleaned. Start with
`worktree status` and `worktree audit`, then configure allowed roots and
Provider mapping through an approved plan and explicitly submit a
`worktree-adopt/1.0` manifest. A legacy config with embedded roots
remains readable for audit but enforced allocation is blocked until configure
migrates those roots to the host-local binding. A new clone of an enforced
repository must likewise approve its own binding. Resolve
duplicate/orphan/dirty findings explicitly before enabling allocation.
Existing v1 configs without `managementBranch` keep the legacy behavior that
treats the command checkout as management; migrate them with a hash-approved
configure plan before relying on detached Review audit.

## Non-goals

- a hosted control plane or background daemon;
- embedded credentials;
- automatic remote branch deletion;
- force cleanup;
- automatic legal or asset disposition;
- hard-coding one repository, Project, game engine, or coding agent;
- pretending GitLab, Jira, or Codex Thread integration exists before a tested
  adapter is available.
