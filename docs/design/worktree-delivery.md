# Worktree Delivery Governance

## Product boundary

Worktree Delivery is a stack-independent capability in the
`@realpkuasule/harness-automation` package. It reuses the v2 policy compiler,
canonical SHA-256 plans, argv execution, atomic writes, drift checks, rollback,
and receipts.

It is exposed through two Skill entry points:

- `harness-automation` initializes repository policy;
- `manage-worktree-delivery` operates worktree lifecycle through the shared CLI.

The default is audit-only. Installing or upgrading the package creates no
worktrees and deletes no state. Persistent configure, allocate, and close
operations require dry-run planning and exact-hash apply.

## Layers

### Policy plane

`.harness/worktree-delivery.json` is generated by an approved configuration
plan. It records mode, capacity, lease/review/remote retention, allowed and
protected roots, remote deletion policy, and Provider mapping.

Policy v2 also supports optional orthogonal arrays:

```json
{
  "deliveryProfiles": ["worktree-delivery"],
  "domainProfiles": ["game-development"]
}
```

Neither array changes `StackProfile` or inferred stacks. Domain profiles only
append constraints.

### Observation plane

The service obtains machine-readable Git state with argv calls:

- `git rev-parse --show-toplevel`;
- `git rev-parse --path-format=absolute --git-common-dir`;
- `git worktree list --porcelain -z`;
- `git status --porcelain=v1 -z`;
- `git for-each-ref` and `git rev-list`.

Paths are canonicalized before comparison. Read-only status and audit do not
create `.harness`, common-dir state, worktrees, branches, or locks.

Observed state separates:

- `configured`: an approved worktree config exists;
- `loaded`: Git state and configuration were parsed;
- `enforced`: a deterministic checker is available;
- `passing`: the current observation satisfies the checker.

The canonical observation hash includes config hash, refs, worktree state,
leases, Provider observation, and parse errors. Main-checkout dirty state is
excluded because writing the immutable plan itself would otherwise invalidate
that plan; managed worktree dirty state remains included.

Audit rejects secondary worktrees without leases, leases without matching
worktrees, Project-backed Issues missing from the configured Project, and
leases whose heartbeat exceeds `leaseTtlHours`.

### Runtime plane

Repository-scoped runtime state lives under the resolved Git common dir:

```text
<git-common-dir>/harness/worktree-delivery/
  apply.lock
  review.lock
  leases/<sha256(work-item)>.json
  receipts/<change-id>.json
```

Temporary Review recovery receipts live in the host OS state directory.
Credentials are never stored.

## Lifecycle transactions

### Configure

`worktree configure` writes a plan containing the current config hash and
complete replacement content. Apply rechecks the observation hash and config
hash before an atomic write. Rollback restores the exact previous content.

### Allocate

`worktree allocate` requires a work item, branch, absolute path, owner, and
start point. Planning rejects duplicate work-item leases, duplicate paths,
checked-out branches, protected roots, paths outside allowed roots, Provider
failure, and capacity overflow.

Apply acquires the repository lock, rechecks the complete observation hash,
creates or checks out the branch through `git worktree add`, verifies HEAD, and
then writes the lease. Failure compensates only the clean worktree/branch
created by that same approved transaction.

An applied allocation cannot be deleted with `rollback`; it must pass a new
exact-hash close plan because it may now contain valuable work.

### Close

Close planning requires:

- exactly one lease for the work item;
- a matching path and branch;
- a clean worktree;
- an Accepted Commit equal to current HEAD;
- at least one remote ref containing that commit.

Apply rechecks every precondition, removes the exact worktree without force,
and removes its lease. Local and remote branches remain. Rollback can recreate
the worktree only while its branch still points to the recorded commit.

### Review

Review is explicitly temporary rather than persistent:

1. acquire the one-review repository lock;
2. create an OS temporary directory;
3. add a detached worktree for the exact commit;
4. run one argv command;
5. remove the worktree immediately if clean;
6. preserve it with a durable receipt if dirty or cleanup is unsafe.

A process killed before cleanup leaves an active receipt. `retention-audit`
reports receipts and lease heartbeats older than their configured TTL. It never
force-cleans them.

## Dirty-content evidence

Dirty worktrees block close and automatic cleanup. Read-only observation
records:

- repository-relative path and Git status;
- byte size;
- SHA-256 of file or symlink content;
- size and SHA-256 of the tracked binary patch.

Creating a patch file, tar archive, quarantine copy, or disposition plan is a
separate owner-approved action. Business value, asset rights, legal status,
and long-running debugging value are guidance, not deterministic policy.

## Provider and Agent adapters

The portable baseline has no Provider dependency.

The GitHub adapter uses `gh` with argv and configuration-provided repository,
Project owner/number, status field, and Done values. Project fields are not
hard-coded. GitLab and Jira configuration is accepted but reports `blocked`
until a real adapter is installed.

Agent behavior is CLI-first. Claude Code, Codex, DeepSeek/GLM, and unknown
agents use the same command contract. An optional Codex Thread adapter may add
thread-state evidence later; it cannot weaken the portable lease rules.

## CI boundary

CI normally cannot see development-machine worktrees or common-dir leases.
`check --mode ci` therefore reports host-local workspace enforcement as
`blocked` while continuing repository-visible gates. Session checks run the
real local audit and fail when it does not pass.

## Safety invariants

- one work item has at most one persistent lease;
- management, status, audit, retention audit, and planning create zero
  worktrees;
- Review is detached, temporary, branchless, and serialized;
- all mutation targets are canonical absolute paths;
- remote branch deletion is always disabled;
- no operation uses `rm -rf`, `reset --hard`, worktree force removal,
  `branch -D`, or `git clean -f/-x`;
- apply is locked, drift-checked, and idempotent;
- every lifecycle attempt leaves a durable receipt.

## Compatibility and migration

All Policy v2 profile fields are optional in the JSON Schema, so existing
policies remain valid. Existing stack profiles, custom stacks, CLI commands,
and legacy task-board compatibility remain unchanged.

Existing worktrees are not automatically adopted or cleaned. Start with
`worktree status` and `worktree audit`, then configure allowed roots and
Provider mapping through an approved plan. Resolve duplicate/orphan/dirty
findings explicitly before enabling enforced allocation.

## Non-goals

- a hosted control plane or background daemon;
- embedded credentials;
- automatic remote branch deletion;
- force cleanup;
- automatic legal or asset disposition;
- hard-coding one repository, Project, game engine, or coding agent;
- pretending GitLab, Jira, or Codex Thread integration exists before a tested
  adapter is available.
